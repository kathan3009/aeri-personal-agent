## Product contract

Aeri turns a request such as “Make the pasta in this video, use the tomatoes I have, buy the cheapest acceptable ingredients within 3 miles, and keep the delivered total under $30” into a verified purchase proposal. The user can also photograph or share an item and say “find this for me.” It remembers confirmed household facts, searches multiple retailers, explains the tradeoffs, fills a cart, and can submit an order only after a separate approval of the **final merchant, items, substitutions, delivery choice, and total**. If final-price or availability evidence is missing, Aeri labels it as unknown and asks the user to finish at the merchant.

The user can instead say “nearest,” “organic only,” “this brand,” “pickup today,” “no substitutions,” or “buy my usual size.” Grocery is the first complete vertical; the request, offer, and order models must also support clothing and household goods. The agent must never imply a cheaper *delivered basket* from a cheaper individual item while ignoring fees or extra stores.

The agent currently targets **one configured retailer URL (Instacart by default)**. Exa results are links, not verified stock or prices. ## End-to-end architecture

```text
Mobile voice / text / photo / video / share link
  -> intent and constraints (Mastra + model)
  -> household memory and source evidence (Neon Postgres)
  -> missing quantities / product specifications
  -> Exa discovery of candidate merchants and products
  -> Kernel verification at selected merchants: location, stock, size, price, fees
  -> normalized offers + basket optimizer
  -> user approves a merchant-specific cart plan
  -> merchant adapter fills cart and reads the final checkout summary
  -> user approves the exact final total and purchase terms
  -> controlled order submission OR user takeover at merchant
  -> merchant confirmation / receipt -> delivery reconciliation -> memory update
```

**Discovery is not verification.** Exa finds candidate pages. A retailer API, when available, or a Kernel browser session at the selected local store verifies the current offer. Each offer stores `merchant`, `store/location`, `product URL or SKU`, `brand`, `size`, `quantity`, `unit price`, `in-stock state`, `delivery/pickup`, `fees`, `capturedAt`, and `source`. Unknown fields stay unknown. Search-result snippets never become “live prices.”

### Photo-to-product search

The mobile app lets the user take or share a photo and add a short instruction such as “same brand, smallest size” or “something like this under $20.” A verified vision-capable model reads visible text, packaging, barcode if legible, category, color/material/shape, and uncertainty. Aeri combines that evidence with *confirmed* user preferences (brand, size, dietary restrictions, budget, nearby-store preference, delivery mode), then searches multiple retailers through Exa and retailer-specific discovery. Kernel or a retailer API verifies candidate product images, exact variant/size, local stock, and current all-in price. Aeri shows the photographed item beside its proposed matches with labels such as **exact match**, **likely match**, or **similar alternative** and cites the merchant/source. It asks the user when the photo cannot distinguish a variant; it never assumes a visually similar package is the same size or formulation. This is a single-image path and does not require VideoMemory. The current app does **not** yet have photo capture, image interpretation, or visual-result comparison.

### Retailer-neutral shopping loop

1. **Parse the request.** Create `ShoppingRequest`: normalized needs, budget, optimization (`lowest delivered total`, `nearest`, `fastest`, or `preferred merchant`), brand/type/diet/size constraints, location, delivery or pickup, substitution policy, and deadline. Ask only for missing choices that change the result. Save lasting preferences separately from this one-time request.
2. **Resolve what is already owned.** Subtract only confirmed, reasonably fresh inventory from the needed quantities. Show the subtraction. If kitchen evidence is uncertain, ask the user to confirm it rather than silently skipping an item.
3. **Find candidates across merchants.** Exa discovers product/retailer pages; merchant-specific adapters can use official APIs where access exists. For “nearest,” request device location permission or use the saved ZIP/address, select the actual store/fulfillment location, and calculate distance. A straight-line distance is labeled as such; driving time requires a routing provider. Search at least two viable stores when the query is about price or proximity.
4. **Verify and compare.** Kernel visits the specific store/location and checks item match, package size, stock, current price, minimum order, and checkout fees where visible. Normalize `$/oz`, `$/each`, etc. Reject hard-constraint violations first (allergen, brand-only, size, radius, budget cap). Rank baskets by **item subtotal + tax estimate + service/delivery fees + tip + travel cost if relevant**, then account for delivery time and number of stores. A two-store split wins only if its all-in cost and inconvenience actually improve the result. Put a time-to-live on quotes and recheck before purchase.
5. **Show an explainable proposal.** Example: “Store A: $24.60 estimated delivered, 2.1 mi; Store B: $21.40 pickup, 3.4 mi. Store B is cheaper if you can pick up.” Show exact product, pack size, substitutions, fees, unavailable items, and evidence time. Let the user change the choice before any browser cart work.
6. **Prepare checkout.** A merchant adapter fills only approved products and verifies the resulting cart. It returns `added`, `unavailable`, `substituted`, or `uncertain` per line item. Store-specific selectors and login flows stay inside adapters; the planner sees normalized operations such as `searchProduct`, `selectStore`, `addToCart`, and `readCheckoutSummary`. Do not let an LLM freely click a payment button.
7. **Purchase authorization.** Capture the final merchant checkout screen: exact items, quantities, substitutions, address, slot, fees, tip, tax, and total. The mobile app issues a short-lived, single-use approval bound to that snapshot and a maximum amount. Any price increase, product change, address change, or expiry invalidates it. A deterministic submit action, outside the general browser agent tool, may click the final order button only after this approval and only if the retailer supports a reliable confirmation path. Use a payment method already saved at that merchant; Aeri never receives raw card numbers. If login, MFA, CAPTCHA, payment entry, or reliable final-total verification blocks this path, hand control to the user at the merchant checkout. Never retry order submission blindly; first check whether an order was created.
8. **Close the loop.** Mark `ordered` only on a merchant order ID/confirmation, not on a click. AgentMail can ingest a signed inbound receipt as evidence; the email content itself is untrusted and must be matched to merchant/order/item details. On delivery, compare **fulfilled items and substitutions** with the plan, ask the user to resolve differences, and then add what actually arrived to inventory. A failed or partial order does not update pantry memory.

### Retailer login and visible cart review

Each retailer gets a separate, user-approved Kernel browser profile and Managed Auth connection. Aeri opens the Kernel-hosted login flow in the phone's in-app browser; the user completes password, SSO, or MFA there. The LLM receives neither credentials nor one-time codes. Store only opaque connection/profile IDs and connection state in Neon. Launch the shopping browser with that profile, check whether the session is still valid, and ask the user to reconnect when necessary. A user can disconnect a merchant, deleting Aeri's connection/profile and receiving instructions to revoke any still-valid session at the retailer. Kernel's [Managed Auth guide](https://www.kernel.sh/ai-library/agent-identity-how-to-authenticate-an-ai-browser-agent) describes the profile flow and its limits, including unsupported passkey-only flows. The Free plan currently lists three Managed Auth connections; confirm account limits before connecting more merchants.

The phone's **Review store cart** action opens the *same* Kernel browser session through its interactive live-view URL, displayed by Expo WebBrowser inside Aeri. The user sees the actual merchant page and can correct products or take over. Kernel documents [live viewing and control](https://www.kernel.sh/docs/browsers/live-view); Expo documents the [native in-app browser sheet](https://docs.expo.dev/versions/latest/sdk/webbrowser/). The native browser handoff is now wired in the mobile app, but it still needs an on-device, logged-in retailer rehearsal. The current API persists the token-bearing live-view URL in cart state; replace that with a short-lived server-issued link tied to an authenticated Aeri session before production. Pause browser-agent actions while the user is reviewing, avoid session replay on login/payment screens, and destroy the active browser after checkout or timeout.

Aeri's own cart summary remains visible in Tasks before the handoff. For future agent-submitted orders, close the live view, re-read the merchant's final checkout summary, compare it to the approved plan, and show a **second native approval screen** with merchant, exact items, substitutions, address, slot, tax, fees, tip, and maximum total. The general agent tool cannot press “Place order.” Only a controlled submit operation with a valid one-time approval can do that. Today the user completes payment in the merchant page and records the confirmation number; Aeri never auto-orders. If a merchant blocks automation, login, or total verification, the user takes over rather than Aeri claiming success.

Official retailer integrations can replace individual browser adapters without changing the planner. [Instacart's Developer Platform](https://docs.instacart.com/developer_platform_api/guide/concepts/shopping_list) is one optional shopping-list/deep-link adapter, not Aeri's core. Its developer key and production approval are separate prerequisites; its [getting-started guide](https://docs.instacart.com/developer_platform_api/get_started/overview/) says production access commonly takes 30–40 days. For the hackathon, use Kernel for the merchants we can actually rehearse. Do not promise universal coverage: some sites block automation or hide final totals until login.

## Video understanding and memory decision

**Decision for the hackathon: use Gemini video understanding as the primary perception engine, and add Kathan's private [VideoMemory project](https://github.com/kathan3009/videomemory) as an optional retrieval/evidence layer after the first end-to-end recorded-video flow works.** This is a fit decision, not a judgment that VideoMemory is a poor project. Its local checkout at `/Users/kathan/Desktop/videomemory` can ingest URLs/files, transcribe, index frames with CLIP, select query-relevant moments, make contact sheets, and provide timestamps via Python/MCP. It does **not** itself turn a kitchen walkthrough into a reliable structured inventory, track the same carton across frames, read every tiny label, or infer what is hidden behind an object. A vision model is still needed. Running its Python/ffmpeg/Whisper/CLIP stack beside the current Node API also adds deployment and latency risk for tomorrow. Gemini already accepts uploaded video files, has audio plus visual understanding, and supports timestamped prompts; its public YouTube URL input is a separate preview feature. Google documents [video file and YouTube inputs](https://ai.google.dev/gemini-api/docs/video-understanding). Direct Gemini requires a separate Google API key and may bill separately; it does not consume the Neon Gateway credit. Neon says the Gateway offers Gemini models behind a Neon key, but **Gateway video/file compatibility has not been verified**, so we must not assume the Gateway can replace the direct video API. If a small test proves that native Gateway route accepts our video input, switch the model adapter to the credited Gateway without changing the video-memory domain model.

**All-video input contract:** (1) video recorded in Aeri, (2) a video selected from the phone gallery or shared as a file, (3) a public YouTube link, and (4) other share links only where the source exposes a retrievable file or a permitted import path. Normalize uploaded clips to a supported format such as MP4/MOV/WebM, keep the original source and timestamps, and send files through Gemini's Files API. A YouTube URL can go directly to Gemini's documented URL route. A social URL that cannot be fetched or passed to the model should ask the user to share/upload the clip; do not claim universal URL access. Gemini's documented video formats include MP4, MOV, MPEG, AVI, WebM, WMV, FLV and 3GPP. Its default sampling can miss brief labels or rapid movement, so extract/highlight extra frames or ask for a close-up when a product identity matters.

| Input | Perception | Durable memory written after review | Shopping effect |
| --- | --- | --- | --- |
| Public recipe video link or shared video file | Gemini extracts visible/spoken ingredients, amounts, servings, steps and timestamps; VideoMemory may later index moments for cross-video recall | Recipe with source, timestamped evidence, and extraction time | Scale servings; compare ingredients with pantry; create missing-item needs |
| Recorded kitchen/closet/home walkthrough | Gemini segments the walk into places and visible objects, with timestamps and uncertainty; VideoMemory may later support retrieval across clips | User-confirmed object/location map and inventory events, never an automatic stock count | Avoid buying confirmed owned items; recall where an item was seen; ask about uncertain changes |
| In-app voice update | Speech transcription followed by a structured intent | Explicit inventory update, preference, size, brand, allergy, or correction with source `voice` | Changes future filters and quantities |
| Merchant order and delivery | Order confirmation and actual fulfilled items | Purchase event; inventory only after delivery reconciliation | Prevent repeat buying and improve the next plan |

**First and most important flow: record a video -> Aeri builds a reviewable map.** The user walks past a fridge, pantry, shelf, or closet while speaking naturally. The server stores the clip temporarily, sends it for video understanding, and asks for structured `scene -> location -> object -> attributes -> quantity estimate -> timestamp -> confidence` evidence. It merges duplicate sightings within the clip, distinguishes “I saw this” from “the user owns this,” and compares observations with confirmed memory. The app shows a simple room/shelf map and review cards such as “Pantry shelf: 2 cans of chickpeas (00:12); confirm?” The user can correct name, quantity, brand, location, and expiry before the database records an inventory event. The next scan proposes additions, removals, or changed counts against that baseline. A video cannot reveal hidden items, a sealed package's contents, or a clothing size whose tag is not visible; those stay unknown and the app asks for a close-up or voice confirmation. This is the credible meaning of “map everything”: map **everything visible and interpretable with evidence**, then let the user fill gaps.

The concrete processing path is **phone capture/gallery/share -> Aeri API -> Gemini video understanding -> timestamped observation candidates -> user review/corrections -> Neon object/location and inventory events**. A recipe video follows the same ingest path but uses a recipe schema rather than a household-map schema. A photo uses Gemini image understanding and the product-search path above. Voice uses transcription plus explicit intent. Keep uploaded media only as long as processing requires unless the user opts in to an evidence archive; save source IDs/timestamps and confirmed facts. Do not put raw video bytes in the Neon Postgres state blob. Once this path is real, VideoMemory can index those same source clips for questions like “where did we last see the blue jacket?” without replacing Gemini perception. Test its added retrieval value and local latency before making it a runtime dependency.

The memory record should distinguish `observed`, `user_confirmed`, and `stale`, and retain provenance: `item`, `quantity`, `unit`, `brand/variant`, `location`, `observedAt`, `sourceType`, `sourceId`, `confidence`, and `lastConfirmedAt`. An observation is a **proposal**, never an automatic stock count. A later video should reconcile against the previous state and show additions, removals, and uncertain changes. For example: “I saw one milk carton; last confirmed was two. Did you finish one?” Repeated purchases may suggest a favorite brand, but a brand/size preference becomes durable only when explicitly stated or confirmed. Expiring/perishable counts should be marked stale; the agent asks before relying on them for a purchase.

The current implementation has the upload, extraction, review, and confirmed inventory update, but uses a simple name/quantity record. It still needs source links, timestamps per observation, freshness policy, richer item identity, change reconciliation, and actual-delivery matching. The current Neon store saves one JSON state blob; migrate to versioned relational tables for offers, evidence, approvals, orders, and inventory events before multi-retailer ordering.
